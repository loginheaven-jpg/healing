## 3. 결함별 지시

### 3.1 [치명] 이름 없는 음악 글리프가 소리 없이 버려진다

**증상** — `pdfExtract.ts` 260~276행.

```ts
if (isMusicFont && glyphName) {
  ... geo.glyphs.push(...)
} else if (!isMusicFont && unicodeTrustworthy && item.unicode && ...) {
  ... geo.texts.push(...)
}
```

`isMusicFont`가 참인데 `glyphName`이 빈 문자열이면 **두 갈래 어디에도 걸리지 않고 사라진다.** 기록조차 남지 않는다.

**실측** — `rest_test.pdf`에서 4건이 버려진다.

```
code=51 uni="3" size=19.9 x=112 y=789
code=52 uni="4" size=19.9 x=112 y=779
code=51 uni="3" size=19.9 x=112 y=730
code=52 uni="4" size=19.9 x=112 y=720
```

**박자표 숫자다.**

**지시**

1. `isMusicFont && !glyphName`인 경우를 별도 갈래로 만든다. `item.unicode`가 있으면 그것을 이름 대신 쓴다. 예컨대 `"3"`은 `name: "digit.3"`처럼 정규화한다.
2. `unicode`도 없으면 `geo.droppedGlyphs`에 `{ code, x, y, size }`로 기록한다. **버리더라도 흔적을 남긴다.**
3. `droppedGlyphs`가 비지 않으면 `UNKNOWN_GLYPH` 경고에 개수를 포함한다.

**하지 말 것** — `isMusicFont` 판별 로직(155~166행)을 건드리지 마라. 폰트 이름 패턴과 Differences 패턴 검사는 여러 조판 프로그램을 겪으며 다듬어진 것이다.

**완료 기준** — `rest_test.pdf`에서 `"3"`·`"4"` 4건이 글리프로 잡힌다. 다른 픽스처의 글리프 수가 줄지 않는다.

### 3.2 [치명] 박자표 숫자를 읽지 못한다

**증상** — 3/4 악보가 4/4로 나온다.

**원인** — LilyPond는 4/4를 `timesig.C44` 통합 글리프로 그리지만(그래서 `open_satb`·`three_staff`는 성공), **3/4·6/8 등 숫자 박자표는 개별 숫자로 그린다.** 그 숫자가 3.1의 구멍으로 사라진다.

**지시**

1. 3.1을 먼저 끝낸다.
2. 음자리표·조표 오른쪽 구간에서 **같은 x에 y만 다른 숫자 두 개**를 찾는다. 실측에서 x가 정확히 같고(112) y가 10 차이였다. 위가 분자, 아래가 분모다.
3. x 허용 오차는 오선 간격의 0.5배 이내로 둔다.
4. 오선마다 한 세트씩 나온다(실측 2단 → 2세트). 첫 세트만 채택하고 나머지는 무시한다.
5. 못 찾으면 4/4로 가정하되 `TIME_SIGNATURE_GUESSED` 경고(**severity `warn`**)를 남긴다. 지금은 이 경고 자체가 없다.
6. SMuFL 계열(`timeSig0`~`timeSig9`)도 사전에 함께 넣는다. 뮤즈스코어·피날레 대비.

**완료 기준** — `rest_test.pdf`가 **3/4**로 나온다. `open_satb`·`three_staff`는 4/4를 유지한다.

### 3.3 [치명] 쉼표가 사라져 박 위치가 밀린다

**증상** — 마디 1·3의 총 길이가 3.0이어야 하는데 2.0이다. 첫 음이 `b0.00`에 온다. `b1.00`이어야 한다.

**중요** — 쉼표 글리프는 **이미 추출되고 있다**(`rest_test`에서 `rests.2×8`). 사전에도 있다. `toTimedEvents()`가 쓰지 않을 뿐이다.

**지시**

1. `noteParse.ts`에서 쉼표 글리프에 소속 오선과 마디를 붙인다. 음표와 같은 방식.
2. `toTimedEvents()`에서 쉼표를 이벤트로 포함한다. `notes: []`이고 `duration`은 쉼표 길이인 이벤트로 만든다.
3. 박 누적은 쉼표 이벤트도 전진시킨다.
4. `voiceSplit.ts`에서 `notes.length === 0`인 이벤트는 파트에 음표를 넣지 않고 건너뛴다. 다만 **`rests` 배열에는 기록한다.**
5. `ParseResult.rests`를 채운다. `Record<Part, Rest[]>`이며 정의는 `packages/schema`에 있다.

**쉼표 길이 매핑** — 사전에 이미 있을 것이다. 확인만 하라.

| 글리프 | 길이(4분음표=1.0) |
|---|---|
| `rests.0` (온쉼표) | 4.0 |
| `rests.1` (2분쉼표) | 2.0 |
| `rests.2` (4분쉼표) | 1.0 |
| `rests.3` (8분쉼표) | 0.5 |
| `rests.4` (16분쉼표) | 0.25 |

점(`dots.dot`)이 붙으면 1.5배다. 음표와 같은 규칙이므로 기존 코드를 재사용하라.

**완료 기준**

- `rest_test.pdf` 소프라노 첫 음이 `m1b1.00`.
- 마디별 총 길이가 `{1: 3.0, 2: 3.0, 3: 3.0, 4: 3.0}`.
- `rest_test`에서 `MEASURE_DURATION_MISMATCH`가 사라진다.
- **`closed_chord`·`closed_stems`에서도 `MEASURE_DURATION_MISMATCH`가 사라지는지 확인한다.** 감리에서 이 두 픽스처에도 같은 경고가 있음을 확인했다. 쉼표 결함의 그림자로 보이지만 단정하지 않았다. 사라지지 않으면 원인을 따로 조사해 보고하라.
- 모든 파트의 `rests` 배열이 채워진다.

### 3.4 [중대] 음자리표 옥타브 표시를 인식하지 못한다

**⚠ `docs/TASKS.md`의 기존 완료 기준은 틀렸다. 4장을 먼저 읽어라.**

**사실관계** — `open_satb.pdf`의 테너 65~77은 **정확한 값이다.** LilyPond MIDI와 `ground_truth_open.json`이 모두 그렇다. `VOICE_CROSSING` 경고도 이 픽스처의 실제 내용을 옳게 지적한 것이다.

**진짜 문제** — 파서는 `treble_8`을 인식하지 못한다. 글리프에 `clefs.G×6`만 있고 옥타브 표시가 없다. 결과가 맞는 이유는 `voiceSplit.normalizeOctave()`가 음역을 보고 한 옥타브 내렸기 때문이다. **정확성이 휴리스틱의 우연에 기대고 있다.**

이 취약성이 실제로 드러난 곳이 `closed_hard.pdf`다. 같은 보정이 반대로 작동해 음역이 붕괴했다(S 72~93, T·B 28~64).

**지시**

1. `clefs.G` 아래쪽 오선 간격 1~2칸 안에 숫자 `8`이 있으면 `treble8vb`로 판정한다. 3.1을 끝냈으면 그 숫자가 글리프로 잡힌다.
2. 위쪽의 `8`은 `treble8va`. 아래쪽 `15`는 `treble15mb`(드물지만 대응).
3. `clefs.F`도 같은 방식으로 `bass8vb` 등을 지원한다.
4. **`normalizeOctave()`를 없애지 마라.** 스캔 경로에서는 여전히 필요하다.
5. 대신 **어느 쪽이 옥타브를 결정했는지 기록하라.** `ParseResult.warnings`가 아니라 개발용 로그나 `detail`에 남긴다. 예: `{ octaveSource: "clef" | "range-heuristic" }`.

**완료 기준**

- `open_satb.pdf` 테너가 **65~77을 유지한다**(변하면 회귀다).
- 그 옥타브가 `clef`에서 결정됐다고 기록된다. `range-heuristic`이면 미완이다.
- `VOICE_CROSSING` 경고는 **그대로 남아 있어야 한다.** 이 픽스처의 사실이다.
- 다른 픽스처의 음역이 하나도 바뀌지 않는다.

**새 픽스처를 하나 만들어라.** `treble_8`을 쓰면서 테너가 진짜 테너 음역(52~69)인 악보다. LilyPond로 만들고 MIDI를 정답으로 삼는다. 지금 픽스처는 테너가 비정상적으로 높아 이 결함을 가린다.

```
파일명: tenor_octave.ly / tenor_octave.pdf / ground_truth_tenor_octave.json
```

### 3.5 [보통] 가사가 음절로 나뉘지 않는다

**증상** — `open_satb.pdf`의 "Amazing grace how sweet the sound"가 `A m in gr h sw tt so th sa a re`로 조각난다.

**원인** — `parseScore.ts`의 `extractLyrics()`:

```js
if (last && t.x - last.x < t.size * 0.6) last.text += t.text;
```

두 글자의 **시작 좌표 차이**를 쓴다. 간격이 아니라 앞 글자의 진행폭이다. 라틴 비례폭 글꼴에서 이 값이 폰트 크기의 0.5~0.7배라 임계값 0.6에 걸친다.

**한글에서는 우연히 맞는다.** 정폭(1.0배)이라 항상 임계값을 넘어 글자마다 나뉘고, 한글은 한 글자가 한 음절이다.

**지시**

1. 한글 음절(U+AC00~U+D7A3)은 **무조건 글자마다 나눈다.** 예외 없다.
2. 라틴 문자는 진행폭이 아니라 **실제 간격**으로 판정한다. 각 조각의 폭을 알 수 없으면 폰트 크기와 글자 수로 추정한다.
3. 붙임표(`-`)와 공백을 음절 경계로 삼는다. MusicXML 관례와 같다.
4. **한글 픽스처의 기존 동작을 깨뜨리지 마라.** `pdfExtract.test.ts`의 한글 시험이 계속 통과해야 한다.

**완료 기준** — `open_satb.pdf`에서 `A-ma-zing` 형태로 나온다. 음절 수가 음표 수(29)와 크게 어긋나지 않는다. `kor_tounicode` 시험 통과 유지.

### 3.6 [중대] 성부별 리듬 차이를 검출하지 못한다 (검출만)

**증상** — `closed_hard.pdf`에서 음역이 붕괴한다(S 72~93, A 36~69, T·B 28~64로 동일).

**원인** — `toTimedEvents()`가 같은 x의 음표를 묶고 **최단 음길이를 채택한 뒤 그만큼만 박을 전진**시킨다. 한 보표의 두 성부가 다른 리듬이면 긴 음이 짧게 잘린다.

**완전 해결은 P1 범위 밖이다.** 2차에서 기둥 방향 기반 분리로 푼다.

**지시**

1. 화음 안에 서로 다른 음길이가 섞이면 `POLYRHYTHM_SUSPECTED` 경고(severity `warn`)를 남긴다.
2. 해당 마디 번호를 `measures`에 담는다. 최대 20개.
3. 문구는 이것을 그대로 쓴다.
   > `{N}개 마디에서 성부마다 리듬이 다릅니다. 재생이 정확하지 않을 수 있습니다.`

**완료 기준** — `closed_hard.pdf`에서 이 경고가 뜬다. 정상 픽스처에서는 뜨지 않는다.

### 3.7 [중대] 붙임줄을 처리하지 않는다 (검출만)

벡터 경로에서 이음줄 곡선 검출은 어렵다. **1차에는 하지 않는다.**

**지시**

1. 같은 음높이가 **마디 경계를 넘어 연속**하면 후보로 본다.
2. `TIE_UNSUPPORTED` 경고(severity `info`)를 남긴다.
3. 문구:
   > `이어진 음이 있을 수 있습니다. 재생에서는 나누어 소리 납니다.`

**오탐이 나기 쉽다.** 같은 음을 두 번 치는 것과 구별되지 않는다. `info` 등급이라 신뢰도 감점이 2점뿐이니 감수한다. **경고가 10건을 넘으면 하나로 합쳐 개수만 알린다.**

### 3.8 [보통] 무시할 글리프를 사전에 등록한다

`rest_test.pdf`의 `UNKNOWN_GLYPH` 원인이 `brace210`이다. 큰괄호라 음악적 의미가 없다.

**지시** — `glyphDict.ts`에 "무시" 종류를 만들고 아래를 넣는다.

| 글리프 | 정체 |
|---|---|
| `brace*` | 큰괄호 |
| `brackettips.up` / `brackettips.down` | 대괄호 끝 |
| `pedal.*` | 페달 표시 |
| `scripts.*` (당장 필요 없는 것) | 아티큘레이션 |

**진짜 미해석 글리프가 이런 잡음에 묻히지 않게 하는 것이 목적이다.** 무시 글리프는 `unknownGlyphNames`에 넣지 않는다.

**완료 기준** — `rest_test.pdf`에서 `UNKNOWN_GLYPH`가 사라진다.

### 3.9 `ParseResult`를 schema 정의로 교체한다

`packages/schema/src/parse.ts`가 정본이다. `omr-vector`의 옛 정의를 버리고 이것을 임포트한다.

**추가되는 필드 셋**

| 필드 | 채우는 곳 |
|---|---|
| `rests` | 3.3 |
| `measureBoxes` | 3.10 |
| `tempoBpm` | 아래 |

**`tempoBpm`** — 악보에 적힌 빠르기를 읽는다. LilyPond의 `\tempo 4 = 82`는 `♩= 82` 형태 텍스트로 나온다. 텍스트에서 숫자를 찾되, 못 찾으면 `null`을 넣는다. **추정하지 마라.** 화면이 기본값을 쓴다.

**순서 주의** — 이 교체를 3.1~3.8보다 먼저 하면 매 수정마다 타입 오류를 함께 다뤄야 한다. **마지막에 한 번에 하라.**

### 3.10 마디 좌표(`measureBoxes`)를 산출한다

**자동 스크롤의 전제 조건이다.** 이것이 없으면 P4의 악보 뷰가 성립하지 않는다.

**지시**

1. `staffDetect`와 `systemGroup`이 이미 오선·시스템·마디선 좌표를 안다. 그 값을 쓴다.
2. PDF 좌표계를 **페이지 이미지 좌표계(px, Y 아래로 증가)**로 변환한다. 렌더 배율을 곱하고 Y축을 뒤집는다.
3. 기준 렌더 해상도는 **300DPI**로 고정한다. P2가 그 배율로 페이지 이미지를 만든다.
4. 한 마디의 상자는 그 시스템의 **모든 오선을 세로로 감싸야 한다.** 파트 하나가 아니라 시스템 전체다.
5. 산출에 실패하면 빈 배열을 넣는다. 경고는 남기지 않는다. 사용자가 할 수 있는 일이 없다.

**완료 기준** — 모든 픽스처에서 `measureBoxes.length === measureCount`. 좌표가 페이지 크기 안에 들어온다. `x`가 마디 순서대로 증가하고, 시스템이 바뀌면 `y`가 증가하며 `x`가 되돌아간다.
