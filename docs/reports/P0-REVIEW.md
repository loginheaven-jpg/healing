## 2. 특히 잘한 것

**이식 코드를 해시 단위로 지켰다.** "로직 변경 0"이 사실이다. `.js` 확장자와 픽스처 경로만 바뀌었고, 건드리지 말라고 지정한 세 곳(CTM 추적, 기둥/마디선 두께 판별, 넓은 음역 정책)은 한 바이트도 다르지 않다.

**Prettier를 이 폴더에서 제외한 판단이 옳다.** 서식 변경이 P1의 실제 수정 diff를 묻어 버린다는 이유를 댔다. 지시서에 없던 판단인데 목적을 정확히 이해했다.

**ESLint 경고를 끄지 않고 낮췄다.** `noteParse.ts:511` 미사용 인자를 `error`에서 `warn`으로 내려 보이게 두었다. 숨기지 않으면서 P0를 막지 않는 선택이다.

**`packages/schema`를 계약의 자리로 못박았다.** "두 경로는 같은 `ParseResult`를 만든다"는 규칙에 물리적 위치를 준 것이다. 무엇을 넣고 무엇을 넣지 않을지까지 표로 적어 두었다.

**미완을 숨기지 않았다.** 완료 기준 3번은 web의 `/health`만 요구하므로 기준은 충족했는데, 할 일 5번의 `omr-worker` 서비스 생성이 남았다고 스스로 적었다. 기준을 방패로 삼지 않았다.

## 3. 감리에서 새로 밝힌 것

보고서에 없는 내용이다. **P1의 작업 지시가 바뀐다.**

### 3.1 [중요] 내가 준 P1 완료 기준 하나가 틀렸다

`docs/TASKS.md` P1은 `open_satb.pdf`에서 **"테너 음역 53~65, `VOICE_CROSSING` 경고 없음"** 을 요구한다.

**이 기준이 잘못됐다.** LilyPond가 그 악보로 만든 MIDI를 직접 뽑아 확인했다.

```
트랙1(S): 29음, 음역 72-86
트랙3(A): 29음, 음역 57-70
트랙4(T): 29음, 음역 65-77   ← 실제 울리는 음
트랙5(B): 29음, 음역 38-53
```

정답 파일 `ground_truth_open.json`의 테너도 `[65, 69, 69]`로 시작한다. **현재 파서 출력 65~77이 맞다.**

원인은 LilyPond의 `\clef "treble_8"` 의미에 있다. 이 표기는 **적은 음이 곧 울리는 음**이고, 오선 위 위치만 한 옥타브 올려 그린다. 내가 "적힌 위치대로 읽으면 한 옥타브 높다"고 판단한 것은 반대로 본 것이다.

알토(57~70)가 테너(65~77)보다 낮은 것도 이 픽스처의 실제 내용이다. **`VOICE_CROSSING` 경고는 옳게 뜬 것이지 결함이 아니다.**

**다만 진짜 결함이 그 아래에 숨어 있다.** 3.2 참조.

### 3.2 [중대] 옥타브가 맞는 것은 우연이다

파서는 `treble_8`을 인식하지 못한다. 글리프 목록에 옥타브 표시가 없다.

```
open_satb 글리프: clefs.G×6  clefs.F×2  noteheads.s2×100 ...
```

`clefs.G_8`도, 별도의 '8'도 없다. 그런데 결과가 맞는 이유는 **`voiceSplit.normalizeOctave()`가 음역을 보고 한 옥타브 내렸기 때문**이다. 원시 판독은 77~89였을 것이고, 테너 허용 음역(47~72)을 벗어나 보정이 걸렸다.

즉 **정확성이 휴리스틱의 우연에 기대고 있다.** 음역이 조금만 달랐다면 보정이 안 걸리고 한 옥타브 틀린 채로 나온다. 실제로 `closed_hard.pdf`에서는 이 보정이 반대로 작동해 음역이 붕괴했다(소프라노 72~93, 테너·베이스 28~64).

### 3.3 [치명] 박자표 숫자가 통째로 버려지는 지점을 찾았다

`rest_test.pdf`(3/4)가 4/4로 읽히는 원인을 코드 수준에서 특정했다.

`pdfExtract.ts` 260~276행이 이렇다.

```ts
if (isMusicFont && glyphName) {
  ... geo.glyphs.push(...)
} else if (!isMusicFont && unicodeTrustworthy && item.unicode && ...) {
  ... geo.texts.push(...)
}
```

**`isMusicFont`가 참인데 `glyphName`이 빈 문자열이면 두 갈래 어디에도 걸리지 않고 사라진다.** 기록도 남지 않는다.

계측을 넣어 확인했다.

```
=== rest_test === 버려진 음악폰트 항목: 4
   code=51 uni="3" size=19.9 x=112 y=789
   code=52 uni="4" size=19.9 x=112 y=779
   code=51 uni="3" size=19.9 x=112 y=730
   code=52 uni="4" size=19.9 x=112 y=720
```

**박자표 "3"과 "4"다.** 같은 x(112)에 y만 10 차이로 세로로 겹쳐 있다. 정확히 분자·분모다. 오선 2단이므로 2세트가 나온다.

`open_satb`는 0건이다. 4/4를 LilyPond가 `timesig.C44` 통합 글리프로 그리기 때문에 사전에 걸린다. **3/4·6/8 같은 숫자 박자표만 실패한다.** 성가에서 가장 흔한 박자다.

### 3.4 쉼표 결함의 정확한 수치

```
소프라노: m1b0.00d0.5p70  m1b0.50d0.5p70  m1b1.00d0.5p72  m1b1.50d0.5p70
          m2b0.00d3p67  ...
마디별 총 길이: {1: 2.0, 2: 3.0, 3: 2.0, 4: 3.0}
```

**음높이는 전부 정확하다**(Bb4=70, C5=72, G4=67, Ab4=68). 4분쉼표가 사라져 마디 1·3이 2.0이 됐고 첫 음이 `b0.00`에 왔다. `b1.00`이어야 한다.

글리프는 이미 추출된다(`rests.2×8`). **`toTimedEvents()`가 쓰지 않을 뿐이다.**

### 3.5 `MEASURE_DURATION_MISMATCH`가 정상 픽스처에서도 뜬다

`closed_chord`·`closed_stems`(신뢰도 95)에서도 이 경고가 뜬다. 쉼표 결함의 그림자로 보인다. 쉼표를 고치면 사라질 것이다. **고친 뒤 사라지는지 확인해야 한다.**

### 3.6 `brace210`이 미해석 글리프로 잡힌다

`rest_test`의 `UNKNOWN_GLYPH` 경고 원인이다. 큰괄호(brace)라 음악적 의미가 없다. 사전에 "무시" 항목으로 넣어 경고를 없애야 한다. 진짜 미해석 글리프가 이것에 묻힌다.
