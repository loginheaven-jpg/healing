# OMR — 악보 인식

이 문서는 **실측 데이터에 기반합니다.** 추정으로 쓴 부분은 그렇다고 표시했습니다.

---

## 1. 두 경로를 두는 이유

악보 소프트웨어(피날레·시벨리우스·뮤즈스코어·릴리폰드)가 출력한 PDF는 **인식할 필요가 없습니다.** PDF 폰트의 Encoding Differences 배열에 `noteheads.s2`, `clefs.G` 같은 글리프 이름이 그대로 들어 있습니다. 읽어서 해석하면 됩니다.

| 경로 | 입력 | 방법 | 실측 속도 | 실측 정확도 |
|---|---|---|---|---|
| 벡터 | 악보 소프트웨어 PDF | 글리프 이름 해석 | 0.4~0.9초/쪽 | 음정·리듬 100% |
| 이미지 | 스캔·사진 | Audiveris | 100초/쪽 | 구조 100%, 가사 부분 |

**벡터 경로를 먼저 시도하고, 실패할 때만 이미지 경로로 갑니다.**

## 2. 엔진 비교 실측

같은 입력, 같은 정답으로 세 엔진을 측정했습니다.

### 2.1 통제 실험 — 깨끗한 300DPI 조판 악보

정답: SATB 4파트, Eb장조 3/4, 4마디, 음표 40개, 가사 40음절.
(`packages/omr-vector/fixtures/reference_satb_*` 참조)

| 엔진 | 보표 | 마디 | 조표 | 박자 | 음표 | 리듬 | 음정 | 가사 | 시간 |
|---|---|---|---|---|---|---|---|---|---|
| **Audiveris 5.9.0** | 4/4 | 4/4 | 정확 | 3/4 | 40/40 | 100% | 3파트 100% | **12음절** | 100초 |
| **homr 0.7.0** | 4/4 | 4/4 | 정확 | 3/4 | 40/40 | 100% | 3파트 100% | 0 | 150초 |
| oemer | **1/4** | **17/4** | 정확 | 미검출 | 41/40 | — | 79.2% | 0 | 600초 |

세 엔진 모두 테너에서 한 옥타브 오류가 났습니다. 옥타브 낮은 높은음자리표(`treble_8`)를 인식하지 못하기 때문이며, 엔진의 결함이라기보다 공통 한계입니다. 후처리로 잡습니다.

### 2.2 실전 — 실제 스캔본 119DPI

| 엔진 | 보표 | 마디 | 박자 | 가사 |

**homr가 실전에서 무너진 지점** — 로그에 오선 이미지 5개를 인식하고도 `Finished parsing 1 staves`로 끝났습니다. 합창 2단과 피아노 2단을 한 덩어리로 합쳤습니다. 시스템 그룹화가 약합니다.

## 3. 해상도 한계선

**이것은 추정이 아니라 측정값입니다.**

실제 스캔본을 측정한 결과 오선 간격이 **7.0px**이었습니다. 동일한 악보를 300DPI로 조판해 112DPI로 축소한 대조군을 Audiveris에 넣었더니, 엔진이 스스로 처리를 중단하며 이렇게 말했습니다.

```
With a too low interline value of 8 pixels, either this sheet contains no
multi-line staves, or the picture resolution is too low (try 300 DPI).
This interline value is NOT RELIABLE!
Sheet flagged as invalid.
```

우리가 만든 독립 오선 검출기도 같은 입력에서 5선을 5개로 세지 못하고 6개 후보를 냈습니다. **사람이 만든 전용 검출기조차 오선 개수를 확정 못 하는 해상도**입니다.

| 오선 간격 | 결과 |
|---|---|
| 18px (전처리 확대 후) | 정상 처리 |
| 10px 이상 | 양호 |
| 8px | Audiveris 자체 거부 |
| 7px (실제 스캔본) | 확대 없이는 불가 |

전처리 확대(119DPI → 300DPI 상당)로 임계값은 넘길 수 있습니다. 실제로 `score1.jpg`는 확대 후 오선 간격 18px를 얻어 처리에 성공했습니다. **다만 정보가 늘어나지는 않습니다.** 구조는 살아나도 가사는 살아나지 않습니다.

### 3.1 가사 인식률의 실측

`score1.jpg` (119DPI, 전처리 확대 후) 결과:

| 항목 | 결과 |
|---|---|
| 제목 "이 세상 험하고" | 7자 중 6자 정확 |
| 빠르기말 "여유있게" | 정확 |
| 가사 (23음절 중) | **5음절** (주·의·대·속·서) |
| 인식된 글자의 정확도 | 100% |

**큰 글씨는 읽고 작은 글씨는 못 읽습니다.** 재현율은 22%지만 정밀도는 100%입니다. 300DPI에서는 '주의은혜', '대속하여'를 글자 오류 없이 읽었습니다.

**따라서 1차에서 가사는 보조 정보입니다.** 악보 뷰가 원본을 보여주므로 사용자는 눈으로 가사를 읽습니다. 가사 OCR은 가창 합성이 들어가는 1.5차에 다시 중요해집니다.

## 4. 이식된 벡터 파서의 구조

`packages/omr-vector/src/` 는 이전 버전에서 옮겨 온 코드입니다. 파일별 역할입니다.

| 파일 | 줄 수 | 역할 |
|---|---|---|
| `pdfExtract.ts` | 452 | PDF 연산자 순회, CTM 추적, 글리프·선·텍스트 추출 |
| `glyphDict.ts` | 198 | 글리프 이름 → 음악적 의미 사전 |
| `staffDetect.ts` | 177 | 수평선에서 오선 검출 |
| `systemGroup.ts` | 270 | 오선을 시스템으로 묶기 |
| `noteParse.ts` | 622 | 음높이·음길이·마디 산출 |
| `voiceSplit.ts` | 472 | 악보 형태 판별, 성부 분리, 옥타브 보정, 이상 검출 |
| `parseScore.ts` | 352 | 전체 조립, 가사 추출, 신뢰도 계산 |
| `types.ts` | 159 | 타입 정의 |

### 4.1 CTM 추적 (건드리지 말 것)

`pdfExtract.ts` 상단 주석에 이렇게 적혀 있습니다.

> pdfjs의 operator list를 순회하면서 CTM을 직접 추적한다. CTM을 무시하면 좌표가 10배 틀린다 — LilyPond는 전역을 0.1배로 축소한 뒤 텍스트마다 10배로 되돌리기 때문이다.

**이 코드는 어렵게 얻은 것입니다.** 리팩터링 대상으로 삼지 마십시오.

### 4.2 기둥과 마디선의 구분 (건드리지 말 것)

`noteParse.ts`가 두께로 둘을 가릅니다.

> 마디선: 두께 0.35, 길이 정확히 오선 높이
> 기둥: 두께 0.25, 길이 21~26 (오선 높이를 넘거나 어긋남)
> 기둥은 마디선보다 얇게 조판된다. 이는 악보 조판의 보편적 관례다.

### 4.3 넓은 음역 정책 (이유를 알고 건드릴 것)

`voiceSplit.ts`의 `PART_RANGE`가 실제 합창 음역보다 넓게 잡혀 있습니다. 주석에 이유가 있습니다.

> 이 값을 좁게 잡으면 정상 악보를 망친다. open_satb.pdf의 소프라노는 C5~C6를 오르내리는 정상적인 성가인데, comfortable 구간을 좁게 두어 중위값이 "1옥타브 높다"고 판정되어 전체가 내려갔다.

**그런데 이 정책이 새로운 문제를 낳고 있습니다.** 5.3절 참조.

## 5. 확인된 결함 7건

**모두 실행으로 확증했습니다.** 재현 방법과 함께 적습니다.

### 5.1 [치명] 쉼표가 사라져 박 위치가 밀린다

**재현** — `packages/omr-vector/fixtures/rest_test.pdf` (4분쉼표 + 8분음표 4개 + 점2분음표, 3/4)

```
악보  : [4분쉼표] 8분 8분 8분 8분 | 점2분
기대  :          b1.00 b1.50 b2.00 b2.50 | b0.00
실제  :          b0.00 b0.50 b1.00 b1.50 | b0.00
```

마디 총 길이가 3.0이어야 하는데 2.0으로 나옵니다.

**원인** — `noteParse.ts`의 `toTimedEvents()`가 음표머리만 이벤트로 만들고, 박 위치를 음길이 누적으로 계산합니다. 쉼표는 이벤트가 아니므로 박이 전진하지 않습니다.

**영향** — 반주와 어긋납니다. 성가대원이 들어올 지점을 놓칩니다. 연습 도구로서 치명적입니다.

**수정 지시**

1. `noteParse.ts`에서 쉼표 글리프(`rests.*`, `restWhole` 등)를 `RawNote`와 같은 방식으로 수집한다. 사전(`glyphDict.ts`)에는 이미 있다.
2. 쉼표에 소속 오선과 마디를 붙인다. 음표와 같은 방식으로.
3. `toTimedEvents()`에서 쉼표를 이벤트로 포함하되, `notes: []`인 이벤트로 만든다. `duration`은 쉼표 길이.
4. 박 누적은 쉼표 이벤트도 포함해 전진시킨다.
5. `voiceSplit.ts`에서 `notes.length === 0`인 이벤트는 파트에 음표를 넣지 않고 건너뛴다. 다만 `rests` 배열에는 기록한다.
6. `ParseResult.rests`에 파트별 쉼표를 담는다.

**완료 기준** — `rest_test.pdf`에서 첫 8분음표가 `b1.00`에 오고, 마디 총 길이가 3.0이며, `MEASURE_DURATION_MISMATCH` 경고가 뜨지 않는다.

### 5.2 [치명] 박자표를 인식하지 못한다

**재현** — `rest_test.pdf` (3/4 악보)를 넣으면 `timeSignature: 4/4`로 나옵니다.

**원인** — LilyPond는 박자표 숫자를 개별 글리프로 그립니다. `glyphDict.ts`에 통합 글리프(`timesig.C44`, `timesig.C22`)만 있고 숫자 매핑이 불완전합니다.

**영향** — 재생 속도가 통째로 어긋납니다. 3/4과 6/8이 흔한 성가에서 치명적입니다.

**수정 지시**

1. LilyPond(Emmentaler)의 숫자 글리프 이름을 사전에 추가한다. `zero`~`nine`, `timesig.0`~`timesig.9` 등 실제 이름은 `unknownGlyphNames`에 찍어 확인한다.
2. SMuFL의 `timeSig0`~`timeSig9`도 추가한다.
3. 음자리표·조표 직후 구간에서 세로로 두 개 겹친 숫자를 찾아 분자·분모로 조립한다.
4. 찾지 못하면 4/4로 가정하되, `TIME_SIGNATURE_GUESSED` 경고를 남기고 **사용자가 화면에서 고칠 수 있게 한다.**

**완료 기준** — `rest_test.pdf`와 `reference_satb_300dpi.png`에서 3/4로 나온다.

### 5.3 [중대] 옥타브 이조 음자리표를 놓친다

**재현** — `fixtures/open_satb.pdf` (테너에 `\clef "treble_8"`)

```
정답 테너 음역 : 53~65 (실음)
파서 결과      : 65~77
```

정확히 한 옥타브 높습니다. `VOICE_CROSSING` 경고는 정확히 떴지만 `normalizeOctave()`가 고치지 못했습니다.

**원인 두 겹**

1. LilyPond는 `treble_8`을 `clefs.G` 글리프 + 별도의 '8' 문자로 그립니다. `glyphDict.ts`에는 SMuFL의 통합 글리프 `gClef8vb`만 있어 매칭되지 않습니다.
2. `PART_RANGE.Tenor`가 47~72로 넓어, 잘못된 값(중위값 약 71)이 그 안에 들어가 보정이 발동하지 않습니다. **4.3절의 넓은 음역 정책이 이 오류를 가립니다.**

**수정 지시**

1. `clefs.G` 아래 1~2칸 안에 '8' 텍스트나 숫자 글리프가 있으면 `treble8vb`로 판정한다.
2. 같은 방식으로 위쪽의 '8'은 `treble8va`.
3. `normalizeOctave()`는 그대로 둔다. 음자리표를 제대로 읽으면 발동할 필요가 없다.
4. 다만 **테너 전용 추가 검사**를 넣는다. 테너 중위값이 알토 중위값보다 높으면 `VOICE_CROSSING` error를 띄우고 화면에서 [한 옥타브 내리기]를 제공한다. 자동으로 고치지는 않는다.

**완료 기준** — `open_satb.pdf`에서 테너 음역이 53~65로 나오고 `VOICE_CROSSING` 경고가 사라진다.

### 5.4 [중대] 동리듬을 가정한다

**재현** — `fixtures/closed_hard.pdf` (신뢰도 71, 소프라노 음역 72~93으로 붕괴)

**원인** — `toTimedEvents()`가 같은 X의 음표를 묶고 **최단 음길이를 채택한 뒤 그만큼만 박을 전진**시킵니다. 한 보표의 두 성부가 다른 리듬으로 움직이면(소프라노 4분음표 + 알토 8분음표 둘) 소프라노의 4분음표가 8분음표로 축소됩니다.

**영향** — 찬송가류는 대체로 동리듬이라 무사합니다. 편곡 악보에서 무너집니다.

**수정 지시 (1차 범위)**

완전 해결은 1차 범위 밖입니다. **1차에는 검출과 경고까지만 합니다.**

1. 화음 안에 서로 다른 음길이가 섞이면 `POLYRHYTHM_SUSPECTED` 경고(warn)를 남긴다.
2. 해당 마디 번호를 함께 기록한다.
3. 문구: "{N}개 마디에서 성부마다 리듬이 다릅니다. 재생이 정확하지 않을 수 있습니다."

2차에서 기둥 방향 기반 성부 분리로 해결합니다. 벡터 경로에는 기둥 정보가 이미 있으므로(`rects`에서 추출 중) 데이터는 갖춰져 있습니다.

### 5.5 [중대] 붙임줄(타이)을 처리하지 않는다

**원인** — 코드에 tie/slur 처리가 전혀 없습니다.

**영향** — 이어진 음이 다시 소리 납니다. 미디 연습에서는 견딜 만하지만, 가창 합성에서는 멜리스마가 깨져 치명적입니다.

**수정 지시 (1차 범위)**

1. 벡터 경로에서 이음줄 곡선을 검출하기는 어렵다. **1차에는 하지 않는다.**
2. 대신 **같은 음높이가 마디 경계를 넘어 연속**하면 후보로 보고 `TIE_UNSUPPORTED` 경고(info)를 남긴다.
3. 문구: "이어진 음이 있을 수 있습니다. 재생에서는 나누어 소리 납니다."

이미지 경로(Audiveris)는 MusicXML에 `<tie>`를 내므로 **이미지 경로에서는 처리한다.** 변환기에서 tie로 이어진 음을 하나로 합칩니다.

### 5.6 [보통] 가사 병합 임계값이 잘못됐다

**재현** — `open_satb.pdf`의 "Amazing grace how sweet the sound"가 `A m in gr h sw tt so th sa a re`로 조각납니다.

**원인** — `parseScore.ts`의 `extractLyrics()`:

```js
if (last && t.x - last.x < t.size * 0.6) last.text += t.text;
```

두 글자의 **시작 좌표 차이**를 씁니다. 글자 사이 간격이 아니라 앞 글자의 진행폭입니다. 영문 비례폭 글꼴에서 이 값이 폰트 크기의 0.5~0.7배라 임계값 0.6에 걸칩니다.

**한글에서는 우연히 맞습니다.** 한글은 정폭(1.0배)이라 항상 임계값을 넘어 글자마다 나뉘고, 한글은 한 글자가 한 음절이므로 결과가 옳습니다.

**수정 지시**

1. 진행폭이 아니라 **간격**으로 판정한다. 각 텍스트 조각의 실제 폭을 알 수 없으면, 폰트 크기와 글자 수로 추정한다.
2. 한글(U+AC00~U+D7A3)은 무조건 글자마다 나눈다. 한 글자가 한 음절이다.
3. 라틴 문자는 붙임표(`-`)와 공백을 음절 경계로 삼는다. MusicXML 관례와 같다.

**완료 기준** — `open_satb.pdf`에서 `A-ma-zing` 형태로 나온다. 한글 픽스처에서 기존 동작이 유지된다.

3.1절 참조. **`pdfjs-dist`를 정확히 `4.10.38`로 고정하십시오.**

## 6. 신뢰도 계산

0~100 정수. 화면에서 오선 게이지로 표시합니다.

```
기본 100
  - error   1건당 -20
  - warn    1건당 -8
  - info    1건당 -2
  - 파트 수가 4가 아니면 (단성부 악보 제외) -15
  - 마디 길이 불일치 비율 × 30
  - source === "image"이면 -5
하한 0, 상한 100
```

**`source === "image"`에 감점하는 이유** — 이미지 인식이 벡터보다 근본적으로 불확실합니다. 사용자에게 "더 확인해 보라"는 신호를 주는 편이 정직합니다.

**해결된 경고(resolved)는 감점에서 제외합니다.** 사용자가 확인하면 점수가 올라갑니다.

## 8. 이미지 경로 → ParseResult 변환

Audiveris가 낸 `.mxl`을 공통 스키마로 옮깁니다.

| MusicXML | ParseResult |
|---|---|
| `<part>` 순서 | 오선 순서. `voiceSplit.detectLayout()`으로 형태 판별 |
| `<note><pitch>` | `Note.p` (MIDI) |
| `<note><duration>` + `<divisions>` | `Note.d` (4분음표=1.0) |
| `<rest>` | `Rest` |
| `<measure number>` | `Note.m` |
| 마디 내 누적 | `Note.b` |
| `<lyric><text>` | `lyrics[]` |
| `<key><fifths>` | `keyFifths` |
| `<time>` | `timeSignature` |
| `<tie>` | 이어진 음을 하나로 합침 |
| `<sound tempo>` 또는 지시어 텍스트 | `tempoBpm` |

**주의 세 가지**

1. **Audiveris는 성부(voice)를 자주 틀립니다.** MusicXML의 `<voice>`를 믿지 말고, 벡터 경로와 같은 규칙(음높이 정렬)으로 성부를 나누십시오. `voiceSplit.splitClosedScore()`를 재사용합니다.
2. **파트 이름을 믿지 마십시오.** Audiveris는 `Voice`, `P3-Staff1` 같은 이름을 붙입니다. 음자리표와 화음 밀도로 판별하십시오.
3. **가사가 덩어리로 나옵니다.** 실측에서 '주의은혜'가 한 덩어리였습니다. 한글은 글자마다 나누고, 마디·박 위치는 붙어 있던 음표에서 가져오십시오.

## 9. 알려진 한계 (1차에서 해결하지 않음)

| 항목 | 상태 | 대응 |
|---|---|---|
| 중간 전조 | 미지원 | `KEY_CHANGE_UNSUPPORTED` 경고 |
